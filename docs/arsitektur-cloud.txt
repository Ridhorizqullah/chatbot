# Arsitektur Lengkap TaniPintar Bot

Saya sarankan TaniPintar dibangun dengan pendekatan Cloud-Native, Modular Monolith, dan Event-Driven Processing. Jadi, sistem tetap punya pemisahan komponen yang jelas, tetapi tidak langsung dibuat menjadi banyak microservices yang justru membebani VPS 2 vCPU dan RAM 2 GB.

Target arsitektur yang kita gunakan:

- Tencent Lighthouse Singapore: menjalankan backend, WhatsApp gateway, worker, dan reverse proxy.
- Tencent CloudBase PostgreSQL PG Mode: menggantikan Supabase untuk database, autentikasi, RLS, dan vector database.
- Tencent Cloud Storage: menyimpan foto tanaman dan dokumen pengetahuan.
- Tencent TokenHub: menyediakan LLM, Vision, dan embedding.
- BMKG dan sumber harga pasar terverifikasi: menyediakan data faktual cuaca dan harga komoditas.
- Kubernetes/K3s: disiapkan sebagai tahap pengembangan berikutnya, bukan dipaksakan pada VPS 2 GB.

## 3. Alur kerja setiap fitur

### A. Konsultasi penyakit tanaman melalui teks

1. Petani mengirim pesan WhatsApp: "Daun cabai saya menguning dan menggulung."
2. WAHA meneruskan webhook ke FastAPI.
3. FastAPI memvalidasi webhook, memeriksa duplikasi pesan, lalu memasukkan pekerjaan ke queue.
4. Worker menjalankan LangGraph dan intent router memilih Diagnosis Agent.
5. Diagnosis Agent mengambil pengetahuan relevan dari PostgreSQL dan pgvector.
6. Hy3 menyusun analisis berdasarkan gejala dan sumber pengetahuan yang ditemukan.
7. Jawaban dikirim melalui WAHA dan riwayat konsultasi disimpan.

### B. Diagnosis penyakit melalui foto

1. Petani mengirim foto daun atau tanaman.
2. Foto disimpan di Cloud Storage menggunakan bucket privat.
3. Worker memeriksa ukuran, format, dan kualitas gambar.
4. Vision Model melakukan analisis visual.
5. Visual RAG mencari foto penyakit serupa menggunakan embedding visual dan pgvector.
6. Hasil Vision, gejala, dan referensi pengetahuan digabungkan oleh Diagnosis Agent.
7. LLM menyusun hasil dengan tingkat keyakinan dan langkah penanganan yang relevan.
8. Foto, hasil diagnosis, dan riwayat disimpan; jawaban dikirim ke WhatsApp.

Hasil diagnosis jangan ditampilkan sebagai kepastian mutlak. Jika foto buram atau gejalanya tidak cukup, bot harus meminta foto tambahan atau mengarahkan petani untuk pemeriksaan lapangan.

### C. Informasi harga pasar

1. Petani bertanya harga cabai di wilayahnya.
2. Market Agent membaca data dari sumber harga yang sudah diverifikasi.
3. Price Service memeriksa komoditas, wilayah, satuan, dan tanggal pembaruan.
4. LLM hanya membantu menjelaskan data tersebut.
5. Bot mengirim harga, lokasi, satuan, tanggal data, dan sumber.

Aturan wajib: jangan mengisi harga yang tidak tersedia dengan angka buatan AI. Bedakan data aktual, data historis, dan data simulasi.

### D. Informasi cuaca

1. Petani mengirim lokasi atau memilih wilayah.
2. Weather Service mengubah lokasi menjadi kode wilayah yang dibutuhkan.
3. Service mengambil prakiraan dari BMKG.
4. Jika sumber utama gagal, gunakan fallback yang sudah dikonfigurasi.
5. Bot menjelaskan prakiraan, waktu berlaku, dan sumber data.

### E. Rekomendasi pupuk dan pestisida

1. Petani menyampaikan tanaman, umur tanaman, dan gejala.
2. Fertilizer Agent mengambil katalog dan knowledge base.
3. LLM menyusun rekomendasi berdasarkan data yang tersedia.
4. Sistem menampilkan dosis, cara aplikasi, peringatan, dan sumber referensi jika datanya tersedia.

Untuk pestisida, rekomendasi harus mengacu pada label resmi produk dan aturan penggunaan. AI tidak boleh mengarang dosis atau mencampurkan produk tanpa dasar yang tervalidasi.

### Pembagian schema PostgreSQL

| Schema                                            | Isi                                                              |
| ------------------------------------------------- | ---------------------------------------------------------------- |
| `auth`                                            | Identitas dan autentikasi pengguna                               |
| `public`                                          | Profil, konsultasi, pesan, diagnosis, katalog, harga, cuaca      |

Aturan vector database:

- Embedding teks dan embedding visual disimpan terpisah.
- Jika model embedding teks yang dipilih menghasilkan 1024 dimensi, kolomnya harus `vector(1024)`.
- Jika model visual menghasilkan 2048 dimensi, kolomnya harus `vector(2048)`.
- Jangan mencampurkan embedding dari model yang berbeda dalam satu indeks pencarian.
- Catat nama model dan versi embedding agar proses regenerasi dapat dilakukan.

## 5. Arsitektur keamanan

Ini bagian yang tidak boleh dilewatkan, terutama karena bot berinteraksi dengan nomor WhatsApp dan menyimpan foto petani.

| Area             | Pengamanan                                                               |
| ---------------- | ------------------------------------------------------------------------ |
| WhatsApp webhook | Verifikasi signature/token sesuai jenis gateway                          |
| Admin API        | JWT, role-based access control                                           |
| Database         | RLS dan hak akses minimum                                                |
| Cloud Storage    | Bucket privat dan signed URL dengan masa berlaku singkat                 |
| API              | HTTPS, rate limit, validasi input                                        |
| API Key          | Simpan di environment variable atau secret manager                       |
| Queue            | Job ID unik dan idempotency                                              |
| Log              | Jangan mencatat API key, token, atau isi data pribadi secara tidak perlu |
| Foto             | Validasi MIME, ukuran, dan format file                                   |
| AI               | Validasi output dan larangan mengarang data faktual                      |

Khusus WAHA, jangan membuka dashboard administrasi tanpa autentikasi ke internet publik. Endpoint admin juga tidak boleh bisa diakses hanya dengan mengetahui URL-nya.

| --------- | ------------------------------------------- |

### Contoh struktur Docker Compose

Berikut hanya kerangka deployment, bukan konfigurasi siap produksi:

```
services:
  nginx:
    image: nginx:alpine
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    depends_on:
      - api

  api:
    build: .
    command: uvicorn api.app:app --host 0.0.0.0 --port 8000
    restart: unless-stopped
    env_file: .env
    depends_on:
      - redis

  worker:
    build: .
    command: python -m workers.worker
    restart: unless-stopped
    env_file: .env
    depends_on:
      - redis

  waha:
    image: devlikeapro/waha
    restart: unless-stopped
    env_file: .env
    volumes:
      - waha_data:/app/.sessions

  redis:
    image: redis:alpine
    restart: unless-stopped
    command: redis-server --appendonly yes
    volumes:
      - redis_data:/data

volumes:
  waha_data:
  redis_data:
```

Untuk produksi, tambahkan autentikasi WAHA, health check, batas memori CPU, Redis password, jaringan internal Docker, konfigurasi TLS, rotasi log, serta kebijakan backup. Pastikan path volume WAHA sesuai versi image yang benar-benar digunakan.

## 8. Kubernetes: kapan mulai digunakan?

Saya tetap merekomendasikan Kubernetes, tetapi bertahap.

| Tahapan                    | Infrastruktur               | Teknologi                  |
| -------------------------- | --------------------------- | -------------------------- |
| Tahap 1 — MVP              | 1 VPS 2 GB                  | Docker Compose             |
| Tahap 2 — Stabil           | VPS 4 GB atau lebih         | K3s                        |
| Tahap 3 — Scale            | Beberapa node               | K3s / Kubernetes           |
| Tahap 4 — Production scale | Infrastruktur terdistribusi | Kubernetes + observability |

Saat berpindah ke K3s, komponen dapat dipisah menjadi Deployment, Service, ConfigMap, Secret, PersistentVolume, dan Ingress.

Contoh pembagian workload:

- `tani-api`: FastAPI.
- `tani-worker`: pemrosesan konsultasi.
- `waha`: WhatsApp gateway.
- `redis`: antrean pekerjaan.
- `nginx-ingress`: akses HTTPS.
- `cloudbase`: database eksternal, tidak dijalankan dalam cluster.

Jangan menganggap satu node K3s sudah memberikan high availability. Untuk HA dibutuhkan beberapa node dan rancangan control plane yang sesuai.

## 9. Tahapan migrasi dari Supabase ke Tencent

Saya sarankan migrasi tidak dilakukan sekaligus secara langsung di production.

1. Audit Supabase

   Inventarisasi tabel, relasi, trigger, function, RPC, RLS, bucket, metadata storage, Auth, dan embedding.
2. Bangun CloudBase staging

   Buat environment PG Mode baru di Singapore. Aktifkan ekstensi yang dibutuhkan dan siapkan schema serta kebijakan akses.
3. Migrasi database

   Transfer struktur dan data, kemudian validasi jumlah baris, UUID, foreign key, sequence, trigger, dan function.
4. Migrasi Storage

   Salin objek foto dan dokumen. Validasi path, ukuran, MIME type, checksum, dan kepemilikan.
5. Migrasi Auth

   Pindahkan identitas dan metadata yang kompatibel. Jika password hash tidak kompatibel, gunakan mekanisme reset atau aktivasi ulang.
6. Migrasi AI

   Ganti Gemini dengan adapter TokenHub. Uji chat, vision, embedding, dan Visual RAG secara terpisah.
7. Integration testing

   Uji konsultasi teks, diagnosis foto, harga, cuaca, pupuk, riwayat, dan hak akses pengguna.
8. Cutover

   Hentikan sementara penulisan ke Supabase, lakukan sinkronisasi akhir, ubah konfigurasi aplikasi, lalu pantau sistem.

Jangan menghapus Supabase sebelum semua data dan fitur di Tencent tervalidasi.

## 10. Target kapasitas dan monitoring

Untuk VPS 2 vCPU / 2 GB, target awalnya adalah menjalankan pilot dengan beban ringan, bukan menjanjikan kapasitas pengguna tertentu.

Hal yang perlu dipantau:

| Metrik          | Tujuan                               |
| --------------- | ------------------------------------ |
| CPU usage       | Mengetahui beban API dan worker      |
| RAM usage       | Menghindari OOM kill                 |
| Disk usage      | Mengawasi log dan file sementara     |
| API latency     | Mengukur waktu respons               |
| Queue depth     | Melihat antrean konsultasi           |
| AI latency      | Mengukur waktu respons TokenHub      |
| Webhook failure | Memantau pesan gagal diproses        |
| DB connection   | Mencegah koneksi database berlebihan |
| Error rate      | Menemukan gangguan fitur             |

Prioritaskan juga retry dengan batas percobaan, dead-letter queue, timeout, dan idempotency supaya pesan yang sama tidak menghasilkan konsultasi ganda.
